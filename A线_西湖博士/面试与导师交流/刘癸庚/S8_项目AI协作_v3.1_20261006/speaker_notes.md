# S8 v3.1｜主述

做这个项目时，我开始学习怎么组织自己和多个 Agent 一起工作。

它的起点其实很偶然。那段时间，我经常和 ChatGPT 聊物理、AI、音乐、哲学这些问题。去秦皇岛毕业旅行的前一晚，准备睡觉、半梦半醒的时候，我突然想到：能不能做一个帮助大学生学习物理专业课程的 Agent？如果做得好，也许还可以扩展到更多传统学习场景。第二天到了秦皇岛住处，我就打开电脑，用 Codex 开始做，很快做出了第一个可用的 Demo。Codex 把实现门槛降了很多，让我能直接动手试这个想法。

屏幕上是后来保留下来的一个原型界面。随着项目越来越复杂，一个 AI 窗口已经不适合把所有事情都包下来。我开始把方案、执行、测试、审查、实际使用验收和文书整理等职责分到不同的 Agent、不同窗口里。目标是什么、做到哪里、允许做什么、什么证据才算够，以及最后是否接受这个结果，仍然需要我来判断。

后来我把这些经验往下整理过。比如这里这张是当时抽象出来的一版“九部门模型”。它的重点其实不是说一定要固定分成九个部门，而是希望把不同职责拆开，尤其是不要让同一个 Agent 同时做方案、实现、验证，最后再自己给自己下结论。

下面这张是对应的七阶段生命周期。从立项和拆解，到方案、执行、测试、审查、UAT，再到发布归档。这里我当时比较在意的一点是，它不是一条只往前走的流水线：如果审查发现问题，或者实际使用时出现缺陷，就应该重新回到前面的执行和修复阶段。

所以我后来越来越觉得，真正要组织的不是一群“很能干的 AI”，而是一个能够分工、交接、验证和回退的协作 loop。

当然这些也不是最后定型的东西。后面我还继续尝试过更原子化的 Agent 组织方式，也做过一套外部加载的治理架构，希望连治理规则本身都能够在有边界的情况下继续迭代。不过这部分内容比较多，我今天就不展开了。

后来我决定继续考研。回学校正式备考之前，我又面临了一些新的现实问题……

## Q&A 备查（仅追问时展开）

**一定要九个部门吗？** 不是。这个版本帮助我把职责边界说清楚，核心是执行与审查分开，以及交接时有可检查的证据。实际组织仍应看任务规模和风险。

**后来还做过什么探索？** 我还尝试过更原子化的 Agent 组织方式，以及从外部加载治理规则的架构，也希望规则本身能在有边界的条件下继续迭代。这些属于后续探索，这一页没有展开，也没有把它们表述为已经验证成熟的系统。
