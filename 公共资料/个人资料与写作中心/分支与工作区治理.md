# 分支与工作区治理

## main 的职责

`main` 保存：
- 六线路由基线；
- 公共事实与证明索引；
- 稳定、可复用的个人资料与写作规则；
- 跨路线面试与导师交流中心的共用母版与真实性边界；
- 已完成阶段性整合的路线工作台基线。

`main` 不负责替代每个 PI 的实时草稿空间。面试与导师交流中心只保存 post-reply 的共用 PPT / 口述 / Research Defense 方法；会议时间、PI-specific hook、会后事实和定制稿留在路线 / PI 工作区。

## 活跃分支的职责

一个活跃分支应有明确范围，例如：
- 某路线候选池更新；
- 某一批 PI 首封；
- 某套公共 CV 的受控修订；
- 某轮 eligibility / funding 深查。

完成稳定阶段后，将成果整合回 `main`；下一轮大改优先从新的 main 再开范围清楚的新分支，而不是无限延长旧分支。

## 历史分支

历史分支保留作为审计链：
- 已被 main 吸收；
- 被后续分支取代；
- 针对已经结束的 PI / 局部任务；
- 不再代表当前工作入口。

**不需要为了“整洁”删除历史分支。** 整洁来自明确入口和状态，而不是抹掉历史。

## 合并原则

- 只合并非历史、当前仍代表最新成果的活跃分支。
- 合并前比较与 main 的 ahead/behind、文件范围和祖先关系。
- 分支相互独立时优先保留真实 merge ancestry；不要把几十个文件手工复制成无历史来源的新提交。
- 有冲突时先解决事实与状态语义，再合并；不得用“最新时间戳”自动覆盖。

## 发送状态与 Git 状态分离

Git merge / `READY_REVIEW` / 文件存在都不代表邮件已发送。

外发状态只能由对应路线的联系记录和用户明确事实改变。
